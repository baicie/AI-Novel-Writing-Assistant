# P16.6-R2 安全与恢复复盘

## 1. 凭据隔离

| 检查 | 结论 | 证据 |
| --- | --- | --- |
| 槽位是否按版本命名 | 是（`{provider}#{revision}`，清除用 `...#cleared`） | provider_service/service.rs |
| CAS 失败是否污染旧槽 | 否：先写新槽，失败即删新槽 | cas_failure_keeps_old_secret_and_profile |
| 历史 Run 是否被换钥 | 否：旧槽永不覆盖；删除 Provider 只清当前槽 | replace_moves_to_new_slot_and_keeps_old_for_runs |
| 无密钥远程调用 | 拒绝（只允许 ollama + 回环） | keyless_calls_are_only_allowed_for_local_ollama |
| 已知缺口 | 凭据槽无 GC；主密钥为 0600 文件（既定取舍） | docs/design/P16-CREDENTIAL-LIFECYCLE.md |

## 2. 删除保护（本轮新增）

`delete_provider_guarded` 现在会统计 `workflow_control` 中处于 `queued / running / waiting_approval / paused` 且合同引用该来源的 Run：

- 命中且未强制 → `Conflict`，数据保持不变；
- `force` → 允许删除，但 workflow_run 记录保留，历史审计不被抹掉。

证据：`crates/novel-storage-sqlite/tests/delete_provider_guard.rs`（4 个用例）。

## 3. 路由快照一致性（本轮新增）

- 新增端口方法 `route_snapshot_rows()`；SQLite 适配器在**单个事务**内读取 provider_credential / provider_model / model_binding。
- 应用层 `route_snapshot()` 改为消费该快照，不再连续三次独立查询。
- 证据：`crates/novel-storage-sqlite/tests/route_snapshot_consistency.rs`
  - 4 worker 并发读写 200 轮，断言快照引用完整性（binding → provider/model 必须同时出现）；
  - 最终状态断言指向最后一代配置。

**边界**：provider 与 binding 是两次独立的用户保存动作，中间态是合法配置，因此「Run 一定拿到某次完整配置」不能靠快照单独保证；能保证的是「快照取自同一时刻，不出现跨表撕裂读」。

## 4. 计费安全

| 场景 | 行为 | 证据 |
| --- | --- | --- |
| 401/403/404 | 不重试 | generation_fault_matrix |
| 429 | 重试但次数有上界 | 同上 |
| 500/502/503 | 有界重试后失败 | 同上 |
| 坏 SSE / 截断流 | 直接失败，不提交正文 | 同上 |
| 取消 | 不发请求、不重试 | 同上 + ollama_generation |
| 已知缺口 | 请求已送达但无响应、Worker SIGKILL/重启、提交失败、同 request_id 重复执行未覆盖 | 见旅程矩阵 G |

## 5. 恢复能力复查

- 未完成任务（含等待人工恢复）在删除来源时被阻止 → 恢复路径不会失去密钥或地址。
- 主密钥丢失且目录仍有密文时拒绝重建（上一轮修复，仍在测试保护下）。
- 迁移与历史库恢复：**本轮未验证**（旅程 B = NOT_RUN），这是当前最大的数据安全未验证项。

## 6. 残留风险

1. 旅程 B（历史库升级/恢复）无任何执行证据。
2. 旅程 C/G/H 的关键分支未执行（双 Mock 路由、故障恢复、真实双窗口）。
3. 凭据槽 GC 仅有设计，无实现。
