## 风险

### P0（阻塞发布）

无。

### P1（应尽快处理）

1. **`clientStatusDerivation` ratchet 已过期**。计数 217 对基线 205，在基线提交上即失败。
   需要一轮专门收敛（走到 `pendingManualRecovery` / `checkpointType` / `waiting_approval`
   的单一推断入口），或经人工批准后上调基线。当前状态下 `pnpm --filter @ai-novel/server test`
   无法作为发布门禁。
2. **server 测试需要 `--experimental-sqlite`**。Node 22.12 下 `node:sqlite` 需显式开启；
   `server` 的 test 脚本没有带该 flag，导致两个生产链路测试静默跳过真实校验。
   建议在 `server/package.json` 的 test 脚本里统一加上。

### P2（可接受）

1. 选区改写的「未知计费」记录不会自动清理，长期使用会累积；
   数量很小（每条约 200 字节），但建议增加按时间清理。
2. 位置恢复只覆盖桌面版；网页版使用 sessionStorage，刷新即失效（与原有行为一致）。
3. `ChapterEditorShell.tsx` 983 行，接近但未超过硬阈值。本轮不做拆分以降低回归风险。

## 仍未验证

- Windows 打包产物上的同一批旅程；
- 真实厂商模型（本轮只用 mock，未调用付费模型）；
- 多窗口同时改写同一章；
- 进程被 SIGKILL 打断在「已发出、未回写」窗口时的界面表现（设计上会停在 `sending` 并按未知计费处理）。

## 下一步建议

1. 在 `beta` 上做集成回归（按 `feature → beta → main` 流程）。
2. 单独一轮收敛 `clientStatusDerivation` ratchet，并把 server test 脚本加上
   `--experimental-sqlite`，让 server 门禁恢复可用。
3. 给「未知计费」记录加按时间清理策略（例如保留 30 天）。
4. 桌面打包产物上跑一次 `p17-selection-rewrite` 与 `p17-edit-position`，确认发布包行为一致。
