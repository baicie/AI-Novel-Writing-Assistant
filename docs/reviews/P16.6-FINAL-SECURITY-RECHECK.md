## 1.1 密钥文件与钥匙库的读取优先级

**判定：真实 P1（已修复）**

实际调用路径：

```
OsSecretStore::get  →  优先读 keyring::Entry(..., id).get_password()
                    →  失败才 read_fallback(id)
```

而同文件 `master_key` 的注释与 `put` 的实现都声明「本地加密文件是权威，钥匙库只是副本」。二者矛盾。

可复现影响：密钥轮换后钥匙库里留着旧值 → `get` 返回**过期密钥** → 远端 401，且错误信息无法定位；文件损坏时也会静默返回旧值，掩盖损坏。

修复（`509ede80`）：

- 新增三态读取 `FileSecret::{Missing, Found, Corrupt}` 与纯函数 `resolve_secret`：
  - 文件读到 → 直接用它（文件权威）；
  - 文件存在但解不开 → **返回 `Unavailable`**，不回退钥匙库；
  - 文件不存在 → 才去钥匙库取历史 Keychain-only 数据。
- `OsSecretStore::get` 改为「先文件、后钥匙库」，且只在文件缺失时才调用钥匙库。

测试（`cargo test -p novel-platform --lib`，15 passed）：

| 用例 | 断言 |
|---|---|
| `local_file_wins_over_stale_keychain_copy` | 文件值胜出，过期钥匙库值被忽略 |
| `corrupt_file_fails_instead_of_falling_back_to_keychain` | 文件损坏 → `Err(Unavailable)` |
| `missing_file_still_reads_legacy_keychain_only_data` | 文件缺失仍能读历史钥匙库数据；两者都无 → `None` |
| `rotated_slots_keep_old_and_new_readable` | `gw#1`/`gw#2` 轮换后各自可读，改写 `gw#2` 不影响 `gw#1` |
| `corrupted_ciphertext_is_reported_as_corrupt_not_missing` | 篡改一个字节 → `Corrupt`，不是 `Missing` |

## 1.2 模型编辑 revision 的并发窗口

**判定：真实 P1 TOCTOU（已修复）**

原实现（`provider_registry_adapter.rs`）先单独查 `provider_revision`，再调用 `SqliteKernel::upsert_model`（独立事务写入）。两步之间另一个窗口推进 revision 时，旧 `expected_revision` 仍会被接受。

修复（`509ede80`）：

- 新增 `SqliteKernel::upsert_model_cas`：**在同一个事务里**读 revision → 比较 → UPSERT 模型 → 提交；
- 适配器 `upsert_model` 改走该 CAS；
- 顺带修掉一个覆盖语义缺陷：自动发现写模型时 `user_overrides` 会被写成 NULL，清空用户显式覆盖。改为用户保存写列表（空数组表示清空）、发现写 NULL，并在 UPSERT 里用 `COALESCE(excluded.user_overrides, provider_model.user_overrides)` 保留用户覆盖。

测试（`crates/novel-storage-sqlite/tests/p166_model_revision_toctou.rs`，2 passed）：

| 用例 | 断言 |
|---|---|
| `stale_revision_cannot_write_model_after_concurrent_bump` | 读到 rev=1 后被别人推进到 2，旧版本写模型返回 `Conflict`，且模型未落库 |
| `discovery_upsert_never_clears_user_capability_overrides` | 发现写入后用户覆盖仍在；用户主动清空才变空 |

## 1.3 发现结果合并的并发安全

**判定：当前不可达（记录，不改）**

`apply_discovered_models` 的调用点只有 `crates/novel-storage-sqlite/tests/provider_registry.rs` 的测试，生产代码（`novel-application`、`src-tauri`）没有任何调用。按「不为死代码做大规模重构」的要求，本轮不改其事务结构，仅在此登记：一旦接入生产路径，必须把「读 provider revision + 读现有模型 + 合并 + 写回」放进同一事务，否则会出现 stale discovery 覆盖用户修改。

## 1.4 主密钥文件权限窗口

**判定：真实 P2（已修复）**

原实现 `create_new` → 写入十六进制密钥 → 再 `set_permissions(0600)`。在 `umask 022` 下，写入瞬间文件是 0644，存在短暂可读窗口。

修复（`509ede80`）：创建时用 `OpenOptionsExt::mode(0o600)`，权限在写入敏感字节之前就成立；写完再核验 `mode & 0o777 == 0o600`，不符直接 `Unavailable`（兜底，不静默放行）。

测试：`master_key_file_is_created_with_owner_only_permissions` 断言创建后模式为 `0600`。该用例不修改进程 umask，避免并行测试竞争。
