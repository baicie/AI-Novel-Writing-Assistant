## Phase 1：Server 测试环境收口

### 问题

`automaticAttempt.test.js` 与 `pipelineExecutionLease.test.js` 在文件顶层 `require("node:sqlite")`。
Node 22 下该模块是实验特性，需要 `--experimental-sqlite`；Node 20 完全没有这个内置模块。

### 修复

`server/scripts/run-tests.cjs` 按能力探测决定启动参数：

1. 当前 Node 能直接 `require("node:sqlite")` → 不加参数（Node 24 即如此）；
2. 加 `--experimental-sqlite` 后能 require → 只对含这两个文件的运行加该参数；
3. 两者都失败 → **直接报错退出并列出受影响用例**，绝不静默跳过。

需要 SQLite 的用例按文件内容（`/\bnode:sqlite\b/`）识别，不维护文件名清单：
新增用例不用登记，也不会漏掉。

没有给所有 Node 版本无条件加参数，也没有删除或排除任何用例。

### 版本矩阵

| 位置 | Node 版本 |
| --- | --- |
| `package.json` `engines.node` | `^20.19.0 \|\| ^22.12.0 \|\| >=24.0.0` |
| `.nvmrc` | `20.19.0` |
| `tauri-ci.yml`（`NODE_VERSION`） | 22.12.0 |
| 本机验证环境 | 22.12.0 |

Node 20 上没有 `node:sqlite`，因此保留「明确失败」分支而不是假装通过。

### 归因结论

对以上每个提交执行 `git merge-base --is-ancestor <commit> eff69f22`，全部为真；
`origin/main` 与 `origin/beta` 都指向 `eff69f22`。因此这 12 处增量
**全部是基准分支上已经存在的旧债务，没有一处来自 P17.2 分支**。

反向核对本分支：`git diff origin/main...HEAD -- client/src` 中命中这三个词的
新增行与删除行都是 0。本分支新增的计费语义在 `client/src/api/`，属于守卫排除范围。

### 修复内容

1. **基线校准**：`clientStatusDerivation` 205 → 217，并在基线文件新增
   `adjustments` 记录（`from` / `to` / `measuredAt` / `baselineCommit` / `reason` / `evidence`）。
2. **防基线滞后**：新增守卫用例「baseline matches the base branch」——
   基线值必须等于基准分支（默认 `origin/main`，可用 `DIRECTOR_GUARD_BASE_REF` 覆盖）的实际计数。
   没有可比基准时打印 `skip:` 并返回，不伪装通过。
3. **防随意抬阈值**：新增守卫用例「baseline adjustments carry evidence」——
   每条调整必须与当前基线值一致、`from < to`、带日期、原因 ≥ 40 字与可复核证据。
4. **可复核工具**：`server/tools/measure-client-status-derivation.cjs` 与守卫共用同一
   正则与排除范围，支持工作区与任意 git 引用。
5. **守卫自身可跑完**：基准分支校验原先对每个文件单独 `git show`，一次要起上百个 git 进程
   （实测约 6 分钟），慢到不会被日常执行，等于没有防回归作用。改为一次
   `git cat-file --batch` 读取整棵基准树，同一 HEAD 上 14 个用例 6.8 秒跑完，断言不变。

### B. 候选采纳快照

桌面内核没有整书快照，采纳前的保护由**章节修订**承担。复核结论：

| 要求 | 机制 | 验证 |
| --- | --- | --- |
| 采纳前正式正文不提前变化 | 保护调用只是 no-op，正文只在 `save_user_chapter` 时写入 | `accepting_a_candidate_adds_a_recoverable_revision_without_touching_the_original_first` |
| 采纳后生成可恢复的历史修订 | 每次保存插入 `chapter_revision` 行 | 同上（原文可在修订列表找回） |
| 保存失败不丢原文 | CAS 比较在事务内、插入之前；失败直接返回 `Conflict` | `a_stale_save_is_rejected_and_never_destroys_the_current_text` |
| 多窗口冲突不覆盖 | `expected_version` 严格相等 | `concurrent_writers_cannot_overwrite_each_other` |
| 回退修订不破坏后续版本 | 回退写入新修订而不是改写历史 | `restoring_an_older_revision_keeps_later_versions_reachable` |
| 过期回退被拒绝 | 回退同样做版本 CAS | `a_restore_based_on_a_stale_version_is_rejected` |
| 不把 no-op 伪装成快照成功 | 只有 `chapter-editor:` 前缀的内部调用降级；作者主动创建快照仍返回 501 | `desktopSnapshotProtection.test.mjs`（1 个用例，含 8 组断言） |

**本轮修正的真实缺陷**：初版降级对**所有** POST 快照生效，会让
`VersionHistoryTab` 的「创建快照」按钮假成功。现在按标签前缀区分，
并把这个判定抽成 `isEditorSnapshotRequest` 做确定性验证。
