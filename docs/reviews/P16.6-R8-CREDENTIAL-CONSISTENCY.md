# P16.6-R8 凭据一致性验收

> 生成时间：本轮 R8 执行期间；分支 `feat/p16-6-provider-hardening`；验收 HEAD `43a3c564`。所有数字均来自本次真实执行。

## 实现顺序（源码事实）

`upsert_provider_with_confirmation`：写 Credential Intent → **数据库 CAS 提交** → 写 CredentialVault → 成功则 Intent done；Vault 失败则**补偿回滚**数据库到 previous profile（或删除新建行），Intent 置 pending。

## 故障矩阵

| 场景 | 用例 | 结果 |
|---|---|---|
| Vault 写入失败 | `vault_write_failure_keeps_old_credential_readable` | 数据库回到 `gw#1`，地址回到旧值，旧密钥仍可读，失败者不留任何密钥 |
| 提交前进程崩溃 | `crash_before_commit_leaves_provider_untouched` | 只有 `gw#1`/revision=1，无新增配置，integrity=ok |
| 两进程并发轮换 | `p166_h_concurrent_cas::two_processes_racing_on_the_same_revision_keep_one_key` | 退出码 {0,2}，赢家密钥在 `gw#2`，失败者密钥不入槽，旧槽保留 |
| 旧 Run 使用旧密钥 | `paused_run_keeps_frozen_route_and_old_key_after_rotation` | 旧 Run 始终用旧槽密钥 |

## 明确回答

- CAS 成功但 Vault 失败：数据库被补偿回滚，不会指向不存在的密钥槽。
- 是否必须重输：不需要，旧配置与旧密钥完好；新的替换需要重新保存。
- Intent 是否会永久 pending：失败时置 pending 用于补偿追踪，不阻塞后续保存。
- Clear 与 Replace：Clear 只写空槽标记，不删旧槽；Replace 写新槽，旧槽永不删除。

## 已知限制

revision 在补偿回滚后继续前进（CAS 版本号语义），UI 端需按最新 revision 刷新，不属于内容错误。
