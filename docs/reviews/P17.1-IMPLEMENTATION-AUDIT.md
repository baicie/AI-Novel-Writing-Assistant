## 上一轮审计的误判（已纠正）

上一轮把 Task 5 记为「需要 chapter-editor 请求的本地 Mock 脚本」，即认为只缺测试脚手架。核实源码后，真实阻塞是**功能在桌面端整条不通**，补 Mock 只会把坏链路固定下来：

1. `previewChapterAiRevisionWithRouting` 的云分支请求 `/novels/:id/chapters/:cid/editor/ai-revision-preview`，而 `desktopApiAdapter` 没有这条路由，落到 `unsupported()` 返回 501「这个功能暂未接入桌面本地内核」；
2. 本地分支由 `localStorage` 的 `local-creation-mode:{novelId}` 开关控制，该开关只在小说编辑页的模式选择器里可切换，章节编辑页没有入口；
3. 即使打开，`handleLocalAiRevision` 调的是 `startGenerationAwaitCheckpoint` → `open_run`，那是整章导演流水线：它不读 `selection`，把 `instruction` 塞进 `promptVersions`（`Record<string,string>`，语义是提示词版本号）当参数传，返回的是整章草稿而非选区候选。

因此本轮按「AI 能力缺失要修能力，不加回退匹配」处理：新增选区改写命令，路由改用 `hasDesktopShell()` 这一真实运行环境判定，不再依赖用户手动开关。

## 关键设计决定

- **AI 调用放 Rust，diff 留 TS。** 候选确认路径 `applySelectedChapterEditorDiff` 会用分片重建原文与候选并逐字比对，两套 diff 实现必然在采纳时报「对比不完整」。因此 `buildChapterEditorDiffChunks` 上移到 `shared/types/chapterEditor/document.ts`，服务端改为从 shared 再导出，全仓只有一份实现。
- **选区坐标双向校验。** 前端按 UTF-16 偏移比对，内核再用 `slice_utf16` 比对一次；不一致就报「请重新选中」，不猜作者想改哪段。
- **不为局部改写多付一次模型请求。** 服务端会先调一次模型解析改写意图，桌面端按作者选择的操作直出意图。
