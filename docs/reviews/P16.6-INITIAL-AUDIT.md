## 2. 逐项核实任务书列出的风险

| 编号 | 风险描述 | 核实结论 | 证据 |
| --- | --- | --- | --- |
| R1 | 内置 Provider 用 `/v1` 作 baseURL，但生成器直接向 endpoint POST，缺 `/chat/completions` | **确认存在（P0）** | `crates/novel-llm/src/catalog.rs` 内置 base_url 为 `https://api.deepseek.com/v1`；`crates/novel-llm/src/provider.rs` 直接 `.post(&request.endpoint)`；旧测试都手写完整 `.../v1/chat/completions` 才通过 |
| R2 | Ollama 是否也拼错路径 | 部分存在：适配器会补 `/api/chat`，但 baseURL 写成 `/v1`（Ollama 的 OpenAI 兼容模式）时被错拼成 `/v1/api/chat` | `crates/novel-llm/src/ollama.rs::chat_endpoint` |
| R3 | 未知协议是否自动落到 OpenAI 兼容 | **确认存在（P0）** | `crates/novel-llm/src/router.rs`：`if protocol == "ollama" {..} else { openai }` |
| R4 | 密钥文件被称为唯一权威，但读取优先 Keychain | **确认存在（P1）** | `OsSecretStore::get` 先读 keyring；主密钥已是文件权威，两者不一致 |
| R5 | Replace/Clear 在 CAS 之前修改当前密钥槽 | **确认存在（P0）** | `upsert_provider` 先 `vault.write` 到 `provider.id` 槽，再 `registry.upsert_provider`；CAS 失败则旧密钥已被覆盖 |
| R6 | 历史 Run 冻结 `credential_ref`，但引用指向可变槽位 | **确认存在（P0）** | 同上：槽位名恒等于 provider id，换密钥会连同历史 Run 一起换 |
| R7 | 密钥文件写入存在「先 0644 后 chmod」窗口 | **确认存在（P2）** | `write_fallback` 先 `fs::write` 再 `set_permissions` |
| R8 | 主密钥丢失但密文存在时被静默重建 | **确认存在（P1）** | `master_key` 找不到文件即生成新密钥 |
| R9 | 密钥文件名清洗可能碰撞 | **确认存在（P2）** | `fallback_file` 把非法字符统一替换为 `_`，`a/b` 与 `a_b` 同文件 |
| R10 | 环节绑定在 Director 链路是否生效 | 已在上一轮修复（`RunContract.step_routes`） | `provider_service/tests.rs` 三条 step_routes 用例 |
| R11 | 模型能力与 UI 绑定是否一致 | 一致：`protocol_supports_generation` 与前端 `GENERATION_READY_PROTOCOLS` 都只允许 openai-compatible / ollama | 两侧源码 |
| R12 | 运行中快照一致性（并发更新产生混合版本） | **仍存在（P1）** | `frozen_step_routes()` 逐条 binding 调 `resolve_route`，每次都会重新读注册表，并发更新可能拼出混合快照 |
| R13 | 无密钥 Ollama 的策略 | 目前 Ollama 适配器不校验密钥，行为上等价「允许无鉴权」，但没有显式策略判定 | `ollama.rs` 不读 `api_key` |
| R14 | 旧合同 legacy 密钥回退范围 | 存在：`credential_ref` 缺失时回退到 `contract.provider` 作为槽位名 | `worker.rs` 各处 `unwrap_or(&claimed.contract.provider)` |

## 3. 本轮已修（详见 FINAL-AUDIT）

- R1 / R2：新增 `novel-llm/src/request_url.rs`，baseURL 与操作路径分离，discovery 与 generation 各有路径构造；7 条真实 HTTP 断言（METHOD/PATH/Auth/BODY）。
- R3：router 改为显式协议分发，未知/只读协议返回 `Unavailable`，且**不发出任何请求**（有用例）。
- R5 / R6：密钥槽按版本命名（`{provider}#{revision}`，清除用 `...#cleared`），先写新槽再 CAS 提交；CAS 失败清理新槽、旧槽与旧配置不受影响；历史 Run 的旧槽永不覆盖/删除。
- R7：写文件改为「0600 临时文件 + rename」，权限先于敏感字节建立。
- R8：主密钥缺失且目录中已有密文时返回错误，不再静默重建。
- R9：清洗改名时追加短哈希，保留旧文件名读取兼容。
- R4：读取权威文档化并统一到「本地加密文件为准，钥匙库仅历史副本兜底」。
