# P17.2 可靠性与性能记录

## 一、长章节对比（P1.2）

### 问题与实测

旧实现 `buildChapterEditorDiffChunks` 用完整二维 LCS 矩阵（`number[n][m]`），复杂度与内存都是
`O(原文 token 数 × 候选 token 数)`。中文按字切分，token 数约等于字符数。

实测（修复前，本机 macOS arm64，Node 22.12，默认堆上限）：

| 章节规模 | 耗时 | 内存 |
| --- | --- | --- |
| 1 万字 | 约 2.4s | 约 630MB |
| 1.6 万字 | 约 13.5s | 约 731MB |
| 3 万字 | 未完成 | JS 堆溢出 |
| 5 万字 | 未完成 | JS 堆溢出 |

本机没有通过放大 Node 堆来掩盖问题。

### 修复方案

`buildChapterEditorDiff(original, rewritten)`：

1. **按码点裁掉公共前后缀**。不能按 UTF-16 单元裁：Emoji 由代理对组成，按单元裁会把半个代理对分到两边，
   产出无法用字符串切片还原的边界。
2. **预算内精确 LCS**：400 万单元格上限，用一维 `Int32Array` 存表（同样单元格数约为二维 `number[][]` 的 1/4 内存）。
3. **超预算退到段落级对齐**：按空行切段，先对齐段落，再在单段落对内部细分（单对 25 万单元格、总计 400 万上限）。
4. **仍超预算则整段替换**，并置 `degraded: true`。

三条不变量：

- 任何路径产出的分片都能逐字重建原文与候选（采纳路径会再校验一次）；
- 小文本与旧实现语义一致（equal/insert/delete + 相邻合并，id 连续）；
- 细粒度不可行时通过 `degraded` 明确告知，`withDiffComplexityNote` 把提示并入候选风险说明。

### 修复后实测

| 场景 | 耗时 | degraded |
| --- | --- | --- |
| 1 万字局部改写 | 1ms | false |
| 3 万字局部改写 | 3ms | false |
| 5 万字局部改写 | 3ms | false |
| 5 万字整段倒序（结构完全不同） | 12ms | true |

局部改写在三档规模下都只产生 1 处可勾选修改，改动量收敛在 10 个原文字符内。

### 覆盖

`shared/types/chapterEditor/document.test.mjs`（11 个用例，全部通过）：

- 中文/CRLF/空白归一化；
- Emoji 单码点替换、重复 Emoji 只删一个、ZWJ 组合序列（👨‍👩‍👧 → 👨‍👩‍👦）；
- 星形平面字符（𝄞）、重复段落；
- 1 万 / 3 万 / 5 万字的局部改写（分片可重建、`degraded=false`、耗时上界、全选后等于候选）；
- 5 万字结构完全不同（`degraded=true`，整段拒绝 = 原文，整段接受 = 候选）；
- 小文本保持逐处对比语义与相邻合并。

彩云与桌面共用同一实现：`server/src/services/novel/chapterEditor/chapterEditorDiff.ts` 只做转发，
`NovelChapterEditorService` 与 `client/src/api/novel/chapterSelectionRewriteModel.ts` 都调用共享函数。

## 二、选区改写的计费边界（P1.3）

### 状态机

| 状态 | 触发 | 含义 | 免确认重试 |
| --- | --- | --- | --- |
| `not_sent` | 密钥 / 校验 / 路由在发送前拒绝 | 确定没有发出 | 可以 |
| `sending` | 已登记、请求进行中 | 进程崩溃会停在这里 | 不可以 |
| `failed` | 已发出且拿到明确失败，或模型返回不可用结果 | 结果可确认，但可能已计费 | 不可以 |
| `unknown` | 超时、连接中断（`billed: true`） | 可能已到达模型服务 | 不可以 |
| `succeeded` | 已拿到候选 | 完成 | 不需要 |

### 关键规则

- 同一条 `requestId` 在 `sending` / `unknown` / `succeeded` 下再次调用返回 `CONFLICT`，
  从源头阻止双击或界面重试造成重复计费。
- 内核用 `AppErrorCode::MODEL_RESULT_UNKNOWN` 表达「结果未知」，前端只按错误码判断，
  不靠错误文案猜。
- 重新生成前若存在未确认请求、或上次结果是 `unknown`，必须经过作者确认；
  提示写明「可能已经发送」「重新生成会再次调用模型」，从不声称「一定没扣费」。
- 章节上方展示未确认请求的可见提示（`chapter-selection-rewrite-unknown`）。
- 未确认请求按 `novel_id + chapter_id` 隔离，不跨章提示。

### 故障注入验证

| 用例 | 断言 | 结果 |
| --- | --- | --- |
| `timeout_is_reported_as_unknown_billing_not_a_plain_failure` | `Timeout` → `ResultUnknown` + `MODEL_RESULT_UNKNOWN`，`retryable=false`，文案含「无法确认」「可能已经发送」 | 通过 |
| `billed_connection_drop_is_reported_as_unknown_billing` | `Unavailable{billed:true}` → `ResultUnknown` | 通过 |
| `explicit_failures_are_not_reported_as_unknown_billing` | Unauthorized / RateLimit / EndpointRejected / `Unavailable{billed:false}` → `Failed`，不得算未知 | 通过 |
| `credential_gate_is_recorded_as_never_sent` | 远程缺密钥 → `NeverSent`，探针调用次数 0 | 通过 |
| `unparsable_model_output_is_not_reported_as_free` | 模型已返回但格式错误 → 不是 `NeverSent`，文案含「已经产生费用」 | 通过 |
| `unknown_result_keeps_blocking_until_explicitly_resolved` | `unknown` 后同 id 再进入被拒；出现在待确认列表 | 通过 |
| `an_attempt_in_flight_blocks_the_same_request_id` | `sending`（进程崩溃残留）也阻止重发 | 通过 |
| `unknown_attempts_are_scoped_to_their_own_chapter` | 两章的未确认请求互不干扰 | 通过 |
| `stored_attempts_never_carry_prompt_or_chapter_text` | 表只有 7 列，无正文/提示词/凭据 | 通过 |
| `definite_failures_are_recorded_without_claiming_unknown_billing` | `not_sent` 不出现在待确认列表 | 通过 |

## 三、本机 Ollama 无密钥（P1.1）

- 复用 P16.6 的 `ensure_credential` / `allow_keyless`，不新建第二套规则；
- 本机回环 Ollama 无密钥可调用，用真实 mock HTTP 服务验证请求落到 `/api/chat` 与 `/v1/chat/completions`；
- 远程 Ollama、OpenAI 兼容、Anthropic 缺密钥时，在发出请求之前拒绝，探针 Provider 调用次数为 0；
- 密钥库不可用按存储错误上报（`STORAGE_CORRUPT`），不伪装成「没填密钥」。

## 四、编辑位置恢复的性能与边界

- 位置上报去抖 400ms，光标与滚动共用同一个调度器；
- 只写 `localStorage`，单个记录约 200 字节，不含正文；
- `pointFromCursorOffset` 对 5 万字正文做全量偏移往返验证，全部一致（段落分隔处归到下一段段首）；
- 正文长度不足原长一半或坐标越界时放弃恢复。
