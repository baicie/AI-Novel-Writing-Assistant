### 1.2 逐条回答

**A. 新旧配置是否可能独立修改同一 Provider？**
会，但只可能落在同一行。旧接口固定写 `id='default'`；新 Registry 的 `upsert_provider('default', …)`
写的也是这一行。区别在于旧接口写 `model` / `secret_ref` / `encoded endpoint`，
Registry 写 `protocol` / `display_name` / `sort_order` / `endpoint`。
（证据：`crates/novel-storage-sqlite/src/model.rs` 的 ON CONFLICT 列表 vs
`crates/novel-storage-sqlite/src/provider.rs` 的 ON CONFLICT 列表。）

**B. 旧接口写入后，Registry 读到什么？**
`list_providers()` 会读到同一行：`endpoint` 与 `allow_localhost_http` 是旧接口写的值，
`protocol` 取迁移默认 `openai-compatible`，`display_name` 为空，
`credential.reference` 等于旧接口写入的 `secret_ref`。`revision` 由 0023 提供初始 0。

**C. 新 Registry 写入后，旧调用路径读到什么？**
`load_model_setup()` 读到 Registry 写的 `endpoint` 与 `allow_localhost_http`；
`model` 列 Registry 不会更新（INSERT 时是空串、ON CONFLICT 不包含该列），
所以旧路径的模型名保持原状——这是刻意的：模型清单属于 Registry，默认模型名属于旧接口。

**D. 重启 / 迁移 / 删除后是否一致？**
- 重启：状态全在 SQLite，无内存单例，一致。
- 迁移：0022（增列 + 两张新表）与 0023（`revision`）都是纯增量；
  `provider_registry::legacy_shaped_default_row_stays_readable` 断言老字段写入仍可读、新列取默认值。
- 删除：`delete_provider_guarded(id, false)` 对「仍被绑定引用」与「id='default'」直接拒绝；
  只有显式 `force=true` 才做级联（model + binding + provider 同事务）。
  裸 `delete_provider` 保留为内部级联，业务入口不应直接调用。

**E. Director 有没有使用新 Registry？**
没有。`director.rs` 的 `provider/model/endpoint` 来自 `DirectorInput` 入参，
`generation.rs` 仍走 `load_model_setup()`，`worker.rs` 用 Run contract 冻结值。
本轮不改这条链路（任务明确「不改造 Director」「不修改 RunContract」）。

### 1.3 采纳的唯一权威方案

**`provider_credential` 是唯一权威存储**（Registry 与旧接口共表，`revision` 作为并发令牌），
旧接口定位为「default provider 的兼容适配器」。不新建配置文件、不引入内存单例。

已知缺口（P1）：旧接口写入时**不**递增 `revision`，所以 Registry 侧 CAS 只能防住 Registry 之间的并发，
防不住「旧接口改完之后 Registry 用旧 revision 覆盖」。补齐方式是把 `save_model_setup` 也改成
`revision = revision + 1`，属于下一步。
