# P16 凭据生命周期与回收设计

目的：把「密钥槽按版本保留」从当前的安全默认，推进到有依据的回收策略。
**本文件只做设计与引用关系审计，不包含任何自动删除实现。**

## 1. 现状

- 槽位命名：`{providerId}#{revision}`；清除动作写入 `{providerId}#{revision}#cleared`。
- 写入顺序：先写新槽 → 数据库 CAS 提交 → 成功后新槽成为当前配置；失败则删除新槽。
- 旧槽不会被覆盖或删除；历史 Run 冻结引用后一直可读。

副作用：每个 Provider 每次换密钥都会留下一个旧槽，长期会累积。

## 2. 引用关系审计

| 引用来源 | 是否持有槽位名 | 生命周期 | 回收影响 |
| --- | --- | --- | --- |
| `provider_profile.credential_ref`（当前配置） | 是 | 随 Provider 存在 | 不可回收 |
| `RunContract.credential_ref`（已提交 Run） | 是 | 与该 Run 记录同生命周期 | 不可回收 |
| `RunContract.step_routes[*].credential_ref` | 是 | 同上 | 不可回收 |
| 活跃 / 暂停 / 待恢复 Run | 同 RunContract | 直到 Run 终态 | 不可回收 |
| Batch 恢复（`batch.rs` 恢复批次） | 通过 RunContract 间接持有 | 直到批次终结 | 不可回收 |
| `credential_intent`（未完成意图） | 是（含新槽名） | 直到 reconcile 完成 | 不可回收（否则补偿失败） |
| 已删除 Provider | 否（记录被删） | 无 | 若无其它引用即可回收 |
| 历史数据库备份 | 是（整库快照） | 与备份同寿命 | 恢复后需要旧槽仍存在，因此备份期内的槽不可回收 |

结论：**任一槽位在「当前配置 / 任一 RunContract / 未完成意图」中出现过，就不可回收。**

## 3. 回收条件（必须同时满足）

1. 槽位名不出现在 `provider_profile.credential_ref`；
2. 不出现在任何 `run_contract.credential_ref` 与 `step_routes[].credential_ref`；
3. 不出现在未完成的 `credential_intent`；
4. 该槽位最后写入时间超过保留期（建议 30 天，可配置）；
5. 同一 Provider 至少保留最近 2 个槽位（保底回滚能力）；
6. 回收动作执行前，先在审计表写一条「待回收」记录并等待一个周期（两阶段删除）。

## 4. 不可回收条件

- 该槽位仍被任何 Run 引用（含已完成 Run 的历史回溯能力）；
- 该槽位属于「已被删除 Provider」但存在历史 Run 引用；
- 用户主动执行「撤销凭据」后，仍需要读旧密钥恢复历史草稿；
- 任何数据库备份快照覆盖的时间窗内。

## 5. 用户主动撤销凭据的语义

- 「撤销」= 当前配置不再使用该密钥（写入 `#cleared` 槽），**不等于删除历史槽**。
- 若用户要求物理删除：需要显式二次确认 + 影响面预览（有多少历史 Run 会失去恢复能力），并在审计日志中记录。

## 6. 审计日志字段（建议）

`槽位名 / providerId / 创建时间 / 最后引用时间 / 引用计数(Run 数) / 状态(active|cleared|orphan|pending_delete) / 操作人 / 操作原因`。

## 7. 可先落地的只读能力（不破坏数据）

- `credential_slot_audit`：列出所有槽位及其引用计数；
- 孤儿槽计数（引用计数为 0）作为面板指标；
- 「回收预览」：只输出将被删除的槽位列表，不执行删除。

## 8. 明确不做

- 本轮不实现自动删除；
- 不在缺少引用计数的情况下删除任何槽位；
- 不因为「槽位看起来旧」而回收 —— 必须同时满足第 3 节全部条件。
