## 5. 连续创建竞态：复现、根因与修复

### 复现结果

在旧构建（beta 基线代码）上：

| 操作 | 观察 |
| --- | --- |
| 两次独立点击（间隔一个 WebDriver 任务） | 第一次点击后按钮立即 disabled，第二次点击无效；只创建 1 章 |
| 同一任务里连续点击 5 次 | 只创建 1 章（请求层未重复） |
| 创建成功后观察按钮 | 按钮持续显示「创建中...」，超过 25 秒仍未恢复 |

因此“连续点击导致重复建章”在当前实现里已被 `isPending` 挡住；真正的用户可见缺陷是
**创建成功后按钮长时间不可用**。这与 P17.4.6 记录的“快速连续点击时按钮可能长时间不可用”
一致。

### 根因

`createChapterMutation.onSuccess` 依次 `await`：

1. `syncNovelWorkflowStageSilently`（工作流状态同步）；
2. `invalidateNovelDetail()`（详情、卷工作区、质量报告、世界切片、人物关系、章节时间线等
   十余个查询逐个失效并重新拉取）。

React Query 要等整个 `onSuccess` Promise 完成才把 `isPending` 置为 false，所以章节已经落库，
按钮仍被锁在「创建中...」。在桌面本地内核上，这些后台刷新叠加后超过 25 秒。

另一个真实缺陷是旧顺序算法 `chapterCount + 1`：删除中间章节后，列表长度与最大章节号脱节，
会生成重复章节号；服务端没有 `(novel_id, sort_order)` 唯一约束兜底。

### 修复（Draft PR #15）

- **同步闸门**：调用瞬间用 ref 拦住同一任务里的第二次创建，不依赖下一次渲染的 `isPending`。
- **先结束创建状态**：章节创建成功后立即结束 mutation；工作流同步与工作区刷新改为后台执行，
  不再阻塞按钮。列表尚未刷新时用 `lastCreatedChapterRef` 记住刚发出的顺序。
- **按书记忆**：`lastCreatedChapterRef` 带 `novelId`；切换小说不会沿用上一本的章节号。
- **失败提示**：`onError` 把真实原因写入章节执行区的状态条；失败后按钮恢复，可直接重试。
- **切书保护**：创建请求在切书后返回时，只刷新原书数据，不把旧章节选中到新书。
- **稳定选择器**：新建按钮与状态条增加 `data-testid`，供回归用例使用。

### 修复后验证

真实桌面 E2E `e2e/p17-4-7-chapter-creation.e2e.js`：

| 用例 | 结果 |
| --- | --- |
| 中文默认标题 + 删除后继续最大编号 | pass |
| 同一任务连续点击只创建 1 章，按钮恢复后可继续 | pass |
| SQLite 排他锁制造写入失败 → 显示「CONFLICT 本地数据库正在写入，请稍后重试。」→ 释放后重试成功 | pass |

失败注入使用独立 Python 进程对 `novel.sqlite` 持有 `BEGIN EXCLUSIVE`，等待真实
`busy_timeout` 到期，不使用固定 sleep 掩盖竞态，也没有修改产品代码制造失败。

## 11. 技术债评估与 P17.5 方向

本轮只评估，不开发：

| 项 | 评估 |
| --- | --- |
| 时间线服务端筛选/分页 | 长篇必需；当前 500 条窗口会把部分数据当完整数据 |
| 伏笔列表分页与截断提示 | 与时间线同一套查询策略，应一起做 |
| 因果边分页 | 数据量小但缺少边界，后续统一分页组件 |
| 旧 Director 伏笔写入 | 没有证据来源，会绕开新的生命周期契约，优先级高 |
| 手工事实可信来源 | 需要明确“作者手工确认”与“原文证据”的关系 |
| SQLite 索引 | `plot_thread(novel_id)` 缺失；千章查询需要观察 |
| 工作台信息架构 | 伏笔能力分散在章节页，缺少全书视角 |

**P17.5 产品方向（建议，不自动开始）**：

1. **全书伏笔总览**：在小说工作台增加书级“伏笔与未回收情节”视图，按未回收、推进中、
   来源失效、待回收章节排序；从每条伏笔跳回证据章节。这是本轮最明确的产品缺口。
2. **服务端分页与筛选前置**：时间线、伏笔、因果边统一游标分页；先筛选再截断。
3. **旧 Director 伏笔入口收口**：所有写入必须走当前证据契约。
4. **章节顺序约束**：服务端唯一约束 + 迁移校验，避免导入/同步产生重复顺序。
5. **Server CI 门禁**：配置 required check 或 always-run gate。
6. 完成人工 GUI 验收与授权模型评测后，再决定是否扩张新功能。
