# P17.4.10-R2 章节义务契约终审修复与 Beta 合并准备

## 结论

**工程状态：`PR23_READY_TO_MERGE`（等待用户明确合并授权；未自动合并）。**

- 新生成的章节计划不再允许静默省略义务：`chapter-list-v2` 的每章必须显式输出
  `obligations`，且至少包含一条 `hard` 义务；缺失、空数组或全 advisory 会先走一次
  结构化修复，仍不合格则 DataIntegrity 暂停，正文不会开始生成。
- hard 与 advisory 在 Writer / Reviewer / Repair 三个环节使用同一套分级语义：
  hard 是不可改写的剧情契约，advisory 是可选建议；只有 advisory 未实现不会触发修复，
  也不会阻塞章节完成。
- 每个 Run 只读取自身 `run_id` 写入的 Context。同章新 Run、作者更新计划、历史 Context
  都不能替换当前 Run 的审校依据；旧 Context 通过 ContextTrace 的来源哈希定位计划版本。
- hard 义务 violation 的 `evidence` 必须在当前候选正文中可定位；无法定位的“证据”会让
  审校 fail-closed，而不是进入修复或伪装成已验证。
- `chapter-draft-v2` 保持原样；新增 `chapter-draft-v3`，把义务槽位放进模板本身，
  消除“版本号不变、渲染后追加”的契约漂移。客户端新 Run 使用 v3，历史冻结 Run 继续用 v2。
- M1 仍为 **FAIL / RETEST_PENDING**，M2–M10 `NOT_RUN`，人工 GUI `MANUAL_GUI_NOT_RUN`。
  本轮没有调用任何真实付费模型。

## 2. 原始缺陷与源码证据

### P1-1 Planner 义务静默缺失

修复前 `normalize_chapter_obligations` 对缺失字段直接返回成功：

```rust
let Some(raw) = object.remove("obligations") else {
    return Ok(());
};
```

`structured_prompt` 固定使用 `chapter-list-v2`，但校验层把“模型漏写”与“历史 v1 计划”
当成同一种情况，于是新计划可以没有任何义务直接进入 Writer。

### P1-2 hard / advisory 分级语义丢失

`render_obligations` 对两类义务都加了标签，但 `draft_prompt` 的追加块统一写成
“本章硬约束义务（必须遵守）”；Repair 模板标题也统一写成“本章硬约束义务”。
advisory 因此被当作硬约束处理，可能触发不必要的修复，或在无法满足时错误阻塞章节。

### P1-3 Context 跨 Run 回退

`latest_run_context_payload` 在找不到当前 `runId` 的 Context 时会回退到“没有 runId 的
legacy Context”。旧版 Context 的 payload 确实没有 `runId`，但产物表里一直有 `run_id`
列；回退逻辑因此无法区分“旧格式的本 Run 上下文”和“其他 Run 的历史上下文”。

### P1-4 版本契约漂移

`chapter-draft-v2` 模板本身没有义务槽位，义务块由代码在渲染后追加。同样的版本号可能
产生两种 Prompt，历史 Run 重放与审计无法只凭版本号判断实际内容。

### P2 Reviewer 证据只靠 Prompt

`obligationId` 已能校验存在性，但 `evidence` 没有被检查是否来自当前候选；Reviewer 可以
引用旧草稿或编造原句而不会被发现。


旧实现把 Run-A 的 legacy Context 交给了 Run-B。恢复按产物 `run_id` 选择后：

```text

test context::tests::a_run_without_its_own_context_never_reads_another_run ... ok
```

## 4. hard / advisory 契约差异

| 维度 | hard | advisory |
| --- | --- | --- |
| Writer | 不可改写的剧情契约 | 可合理取舍的创作建议 |
| Reviewer | 违反必须报告，必须带合法 `obligationId` | 未采用不构成问题；即使报告也不阻塞 |
| Repair | 必须保留关键事件、参与者、因果与顺序 | 可以为了修复 hard 而放弃 |
| 工作流 | 未满足 → 一次有界修复；仍不满足 → 人工审查 | 不触发修复；记录为质量提示 |
| Prompt 分区 | `【硬约束｜必须遵守，不可擅自改写】` | `【创作建议｜可合理取舍，不构成本章失败】` |

实现位置：

- `crates/novel-application/src/obligations.rs`：分区渲染、审校分级、证据定位。
- `crates/novel-application/src/worker.rs`：审校结果按 enforcement 重写
  `issues` 计数；advisory-only 不进入修复。
- `crates/novel-prompt/src/lib.rs`：Writer v3、Reviewer v2、Repair v2 的分级措辞。

Reviewer 返回的 issue 会被补充 `obligationEnforcement` 字段；顶层 `issues` 只统计
需要修复的问题，`advisoryIssueCount` 单独计数。`issueDetails` 仍保留全部问题，便于审计。

## 5. Context pinning 竞态验证

`ArtifactView` 新增 `run_id`，SQLite 读取 `workflow_artifact.run_id`。上下文选择不再依赖
payload 里的 `runId`：

| 场景 | 测试 | 结果 |
| --- | --- | --- |
| A. 同章 Run-A / Run-B 同时存在 | `review_pins_the_context_plan_version_per_run` | 各自读取自己的 Context |
| B. Run-A 进行中，作者更新计划 | `a_reviewing_run_keeps_its_own_frozen_plan` | 审校固定 Run-A 的计划版本 |
| C. Run-B 建立新 Context 后，Run-A 审校 | `a_reviewing_run_keeps_its_own_frozen_plan` | 不读取 Run-B 的计划 |
| D. 当前 Run Context 被删除，历史 legacy 仍存在 | `a_run_without_its_own_context_never_reads_another_run`、`legacy_context_is_attributed_by_artifact_run_id` | 明确失败，不跨 Run 回退 |
| E. 当前 Run 有 Context，但没有 `chapterPlanVersion` | `missing_plan_version_is_recovered_from_trace_hash` | 用 ContextTrace 来源哈希定位旧计划 |
| F. 旧版本 Run 升级后恢复 | `legacy_context_is_attributed_by_artifact_run_id` + 哈希定位 | 通过产物 `run_id` 与来源哈希继续 |
| 无法定位冻结计划 | `unrecoverable_plan_version_fails_closed` | DataIntegrity 暂停，不读最新计划 |

旧 Context 的计划版本恢复方式：ContextTrace 的 `chapter_list` 来源保存了内容哈希；
代码同时尝试“整份计划序列化”和“目标章节计划序列化”两种形式，匹配到才使用该版本。
匹配不到就失败，不会退回“最新计划”。

## 6. Reviewer 证据限制

本轮只做轻量确定性校验：

- hard 义务 violation 的 `evidence` 去除空白、去首尾引号后，必须能在当前候选正文中
  按顺序定位；“……”分隔的多段引用要求每段都存在且顺序一致。
- advisory 引用不做正文定位：未采用建议本来就没有可引用的正文句子。
- 该校验只证明“引用的句子存在于候选”，不判断句子是否真的违反义务；语义判断仍是
  Reviewer 与 M1 人工评审的职责。
- 校验失败会进入 DataIntegrity 暂停（记录 usage、标记 attempt），不会进入修复，
  也不会被当成“零问题通过”。
- `needsAuthorConfirmation`、`violationType`、`sourceRef` 在归一化与分级重写中保留。

仍未解决：evidence 可定位不等于语义正确；Reviewer 可能引用真实句子但做出错误判断。
这是 P2，不能由确定性代码替代。
