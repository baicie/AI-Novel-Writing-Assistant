## 1. 固定输入

### 1.1 用户创作要求

沿用 P17.4.7 M1 样本，避免换题导致不可比：

```text
书名：P17.4.7 模型评测样本
简介：边陲小镇的少年在雪夜发现一枚会发光的旧玉佩，由此被卷入山门与一桩旧案。
预计章节数：30
```

### 1.2 第 1 章目标

```text
第1章：林动在雪夜发现玉佩，随后亲眼撞见老铁匠被灭口。
```

### 1.3 第 1 章义务（复测前由 Planner 输出，允许等价措辞但必须包含同等约束）

| ID | 类型 | 强制 | 内容 |
| --- | --- | --- | --- |
| `ch1-req-1` | required_event | hard | 林动亲眼撞见老铁匠被杀 |
| `ch1-req-2` | required_event | hard | 林动在事件发生时在场 |
| `ch1-causal-1` | causal_constraint | hard | 目击灭口是林动被卷入旧案的直接原因 |
| `ch1-order-1` | ordering_constraint | hard | 先发现雪夜异响，再撞见灭口 |
| `ch1-forbid-1` | forbidden_event | hard | 不得写成“到达时老铁匠已经死亡”或等价的事后到场 |

`advisory` 只允许用于普通氛围、文风与场景细节，不得把关键事件降级为建议。

R2 起，新计划的结构校验要求每章至少一条 `hard` 义务；缺少 `obligations`、空数组或全部为
`advisory` 都会先触发一次结构化修复，仍不合格则 DataIntegrity 暂停，正文不会开始生成。
这条确定性规则只保证“有可执行的剧情契约”，不判断契约内容是否覆盖了全部关键事件；
后者仍由 M1 的人工/授权评审按 4.2 判断。

## 3. 产物保留

每个 Run 必须保留脱敏后的：

1. `story_macro`、`character_cast`、`volume_strategy`、`chapter_list` 产物 JSON。
2. `context` 产物：`promptText`、`chapterPlanVersion`、`obligationIds`、
   `obligationsText`、`trace.sources`。
3. `chapter_draft` / 候选正文。
4. `consistency_review` 的 issueDetails（含 obligationId/evidence/severity）。
5. `chapter_repair` 的输入问题清单与输出正文。
6. Run 状态、usage、pauseSignal、最终候选/章节的 SHA256。
7. 所有 Prompt 的脱敏副本（只保留结构化字段与必要正文，不保留凭据）。

禁止保留：API Key、完整系统凭据、用户真实作品、未脱敏的个人信息。

## 4. 事件一致性判定

### 4.1 确定性检查（必须）

- Planner 的 `chapter_list` 每章都有 `obligations` 数组，且至少一条 `hard`；ID 唯一。
- Context 的 `obligationIds` 与目标章节计划一致；无未来章节 ID。
- Context 的 `chapterPlanVersion` 与目标 `chapter_list` 版本一致；旧 Context 通过
  ContextTrace 的 `chapter_list` 来源哈希定位版本，不读取更新后的计划。
- 每个 Run 只读取自身 `run_id` 写入的 Context；同章其他 Run 或历史 Context 不会被回退使用。
- Reviewer 的每个 hard 义务违反项有 `obligationId`，且 ID 存在。
- hard 违反的 `evidence` 能在当前候选正文中定位（去除空白后逐字匹配）；无法定位 → 暂停。
- 仅引用 `advisory` 的问题不触发修复、不阻塞章节完成，但仍记录为质量提示。
- 无效审校 JSON/未知 ID/伪造证据 → 暂停，不作为零问题通过。
- 修复后复验保留原义务 ID；正文变更不涉及义务本身。

### 4.2 语义检查（人工/授权评审）

- 林动是否在灭口发生时在场，而不是事后到达。
- 老铁匠是否在事件中被杀，而不是此前已死。
- 目击是否成为林动卷入旧案的因果起点。
- 关键事件顺序是否与计划一致。
- Reviewer 的 evidence 是否逐字来自当前候选正文，而不是历史正文。

### 4.3 M1 通过标准

- 无 high 级事件/因果/时间线矛盾。
- hard 义务全部满足，或至少有一次有界修复后收敛。
- Reviewer 的 violation 引用正确 obligationId 与证据。
- 人工/授权评审确认正文可读、事件可理解，并记录修改成本。
- 任一 high 矛盾、义务未满足或审校不可审计 → M1 FAIL。

以下样例用于复测前自检与回归。确定性代码只能判断引用、可定位性与失败路径；
语义是否真的违反义务仍由 4.2 的人工/授权评审判断。

| # | 场景 | 固定输入 | 代码应表现 | M1 判定 |
| --- | --- | --- | --- | --- |
| F1 | 事件符合计划 | 正文含“林动亲眼看见老铁匠被杀”；Reviewer 返回空 issues | 审校通过，无修复 | 可读且无矛盾 → 通过 |
| F2 | 事件事后发生 | 正文含“林动赶到时老铁匠已经死亡”；Reviewer 引用 `ch1-req-1` 且 evidence 为原句 | evidence 可定位，进入一次有界修复 | 修复后仍事后到场 → FAIL |
| F3 | 关键参与者被替换 | 正文写成“苏晚看见老铁匠被杀”；Reviewer 引用 `ch1-req-1` | ID/证据通过确定性校验 | hard 义务参与者错误 → FAIL |

| F7 | Reviewer 伪造证据 | issue 引用 `ch1-req-1`，evidence 为正文中不存在的句子 | 立即暂停，不进入修复 | 审校不可审计 → FAIL |
| F8 | 仅 advisory 未采用 | Review issue 只引用 `ch1-adv-1` | 记录 advisory 提示，不修复、不阻塞 | 不影响 M1 通过 |
