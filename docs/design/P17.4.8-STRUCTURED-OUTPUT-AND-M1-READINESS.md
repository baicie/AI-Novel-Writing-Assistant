## 4. 结构化输出审查结果

审查对象：PR #20 的 `worker.rs`、`worker/worker_validation.rs`、`novel-prompt/src/lib.rs`

### 4.1 归一化

| 输入偏差 | 处理 | 是否保留原意 | 风险 |
| --- | --- | --- | --- |
| `mystery_box` 数组 | 用“；”连接为单个非空字符串 | 保留全部非空文本 | 多谜题被合为一段，损失列表语义，但不编造内容 |
| camelCase 字段 | 重命名为 snake_case；已有 snake_case 优先 | 保留 | 无 |
| 文本字段数组 | 过滤空项后用“；”连接 | 保留 | 列表结构丢失，但文本保留 |
| `conflict_layers` 字符串 | 包装为 `{ "external": 文本 }` | 文本保留 | **把整段文本归入 external 层，属于语义归类假设**（P2） |
| `setpiece_seeds` 字符串 | 包装为单元素数组 | 保留 | 无 |
| 数字/布尔文本字段 | 转为字符串 | 词法保留 | 可能把占位值变成合法文本（P2） |
| 空数组/全空字符串 | 保持原结构，交由校验失败 | 不编造 | 无 |
| 对象/非法类型 | 保持原样，校验失败 | 不编造 | 无 |

结论：归一化不会静默丢失非空文本，也不会凭空生成创作内容；但 `conflict_layers` 的
external 归类与数字/布尔字符串化属于需要产品确认的宽松策略，列为 P2。

### 4.2 一次有界修复

| 检查项 | 结论 | 证据 |
| --- | --- | --- |
| 只允许一次修复调用 | 通过 | 修复分支只调用一次 `generate_with_protocol`；没有循环 |
| 修复 Prompt 含原任务与步骤约束 | 通过 | `structured_repair_prompt` 注入 `original_prompt`、`step_requirement`、`error`、`raw` |
| 修复后完整重新校验 | 通过 | 对 `repair_text` 重新调用 `validate_structured_output` |
| 第二次失败明确终止 | 通过 | `DataIntegrity` 暂停，错误包含首次与修复失败原因 |
| 不会无限循环 | 通过 | 无递归/重试循环；修复失败直接 `return pause` |
| 不会重复提交章节 | 通过 | `execute_structured` 只处理 story_macro / character_cast / volume_strategy / chapter_list / consistency_review，不进入章节 commit |
| usage 正确累计 | 通过 | `accumulate_usage` 合并首次与修复调用的 prompt/completion tokens |
| 超时与错误分类 | 通过（取消见 4.3） | 修复调用失败 → `ProviderUnavailable`；修复结果非法 → `DataIntegrity` |

P2 风险：`consistency_review` 的 JSON 修复如果返回空 `issues`，可能把一次本应失败的
审校变成“无问题”。当前没有“修复过的审校必须人工确认/保留质量债务”的规则；本轮没有
真实发生证据，建议在解除 CI 阻断后补 fail-closed 规则与测试。

### 4.3 取消语义

本轮在 `77935e85` 中已修复并带回归测试：

- 修复调用现在共享首次调用的取消令牌；
- 修复阶段取消进入 `ControlEvent::Cancel` / `run_cancelled`，不再退化为
  `ProviderUnavailable` 暂停；
- 新增 `cancel_during_structured_repair_cancels_instead_of_pausing`，断言 outcome 为
  `Advanced(cancelled)`、`workflow_control.status=cancelled`、且不产生 `story_macro` 产物。

| 场景 | 覆盖方式 | 结果 |
| --- | --- | --- |
| 1. 首次调用前取消 | 既有 run 取消/恢复路径；本轮未新增结构化专用用例 | 既有语义通过；结构化专用用例缺失（P2） |
| 2. 首次调用中取消 | `recovery.rs` 的 draft 取消用例；结构化首次调用分支代码同源 | 通过（文本路径） |
| 3. 修复开始前取消 | 修复调用前无独立窗口；控制取消在步骤边界生效 | 代码审查通过；无专用用例 |
| 4. 修复进行中取消 | 新增 `p8_director_loop` 用例 | 通过 |
| 5. 修复成功后、持久化前取消 | 代码在持久化前不再次检查取消令牌 | 存在窄窗口；结构化步骤只持久化规划/审校产物，不提交章节（P2） |
| 6. Provider 真正不可用 | 首次/修复调用错误分别进入 `ProviderUnavailable` | 代码审查通过；既有 Provider 故障用例覆盖文本路径 |
| 7. 修复返回非法输出 | 代码路径为 `DataIntegrity` 并保留双错误 | 代码审查通过；缺专用自动化用例（P2） |
| 8. 取消后重新开始创作 | 既有 run 控制/恢复用例 | 通过；本轮未改恢复协议 |

结论：没有未解决的 P0/P1；场景 1、5、7 的自动化覆盖仍不完整，列为 P2。

## 8. M1 失败根因与证据

### 8.1 已记录的直接证据

评测记录给出的 high 级矛盾：章节计划第 1 章写“撞见老铁匠被灭口”，正文写成“到达时人已死”。
计划要求主角目击灭口，正文改变了事件参与者与因果顺序。

### 8.2 源码证据

| 观察 | 源码位置 | 对 M1 的意义 |
| --- | --- | --- |
| 目标章节计划是上下文必要来源 | `crates/novel-application/src/context.rs:239-301` | 只要 `chapterOrder == target.sort_order`，计划会进入正文上下文 |
| 章节计划按 `chapterOrder` 匹配 | `crates/novel-application/src/context.rs:130-145` | 匹配失败时会静默放入空来源；M1 的章节序号为 1、计划首章为 1，正常匹配 |
| Writer 提示词只说“不要引入冲突事实” | `crates/novel-prompt/src/lib.rs` `chapter-draft-v2` | 没有把事件顺序、参与者、因果写成硬性约束 |
| `chapter_list` 规划上下文只含卷策略与人物 | `crates/novel-application/src/worker.rs:1750-1756` | 规划阶段没有 `story_macro`，章节计划与故事宏观可能脱节 |
| Reviewer 被要求输出 type/severity/evidence/suggestion | `crates/novel-prompt/src/lib.rs` `consistency-review-v1` | Reviewer 正确识别了 high 级时间线矛盾 |
| 修复提示词只要求“按审校问题修订” | `crates/novel-prompt/src/lib.rs` `chapter-repair-v1` | 修复可改变文本但不保证保持事件顺序；本次修复未解决该矛盾 |

### 8.3 七个候选原因

| # | 候选原因 | 判断 | 证据 |
| --- | --- | --- | --- |
| 1 | Prompt 指令冲突 | 不成立 | 没有相互矛盾的指令；Writer 要求依据上下文 |
| 2 | 上下文信息遗漏 | 部分成立（促成） | 目标章节计划应已包含；但 `chapter_list` 缺 `story_macro`，且计划匹配失败会静默为空 |
| 3 | 模型未遵守计划 | **主因** | 计划与正文的事件因果直接冲突；Reviewer 以此判 high |
| 4 | Planner 与 Writer 契约不一致 | 成立（促成） | Planner 输出短摘要；Writer 没有事件顺序/参与者硬约束；Reviewer 才兜底 |
| 5 | Reviewer 判断异常 | 不成立 | Reviewer 准确报出 high 级时间线矛盾，且与记录一致 |
| 6 | 修复改变原有语义 | 无证据 | 矛盾在修复前的审校中已报告；一次修复后仍有问题；长度 2,217→1,858 只能说明压缩，不能证明引入矛盾 |
| 7 | 验收标准不合理 | 不成立 | 时间线矛盾是长篇连续性的真实质量问题，M1 要求计划遵循合理 |
