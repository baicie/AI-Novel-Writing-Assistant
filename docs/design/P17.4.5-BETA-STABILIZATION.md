## 2. SQLite 非确定性故障

### 2.1 `index_worker_crash`

**现象**

- 完整 workspace 中偶发 `worker did not claim job`，耗时约 19s。
- 旧测试对每个 worker 尝试固定等待 6s，最多 3 次；失败时 3 次都被杀死。

**根因**

- 在正常负载下 worker `open` 40–70ms、`claim` 约 5ms（临时 trace 实测）。
- 主机高负载时（load average 7–11，宿主有 Chrome/虚拟化/安全扩展占用），子进程可被调度延迟超过 6s；
  旧测试在 worker 仍健康时直接 kill，再重试，失败时耗时约 3×6s。
- 不是 worker claim/lease/fencing 的产品缺陷，也不是索引数据损坏；worker 未被杀时会正常 claim。

**修复**

`crates/novel-storage-sqlite/tests/index_worker_crash.rs`：

- 只启动一个 worker，不再 3 次盲目重试；
- 等待真实 marker；worker 提前退出立即失败并输出退出状态；
- 保留 30s 有界安全截止（不是无限延长），正常路径仍以毫秒级 marker 为准；
- 保留 SIGKILL、lease 过期、recover、claim_epoch、chunk 去重与搜索断言。

**重复执行**

- 修复前：高负载下 30 次循环中前 12 次已有 5 次失败（7 pass / 5 fail）。
- 修复后：**30/30 pass**，耗时 1–3s。
- `novel-storage-sqlite` 默认并行：**10/10 pass**，每次 21–46s。
- 默认 workspace：**10/10 pass**（239s / 103s / 89s / 74s / 73s / 79s / 72s / 75s / 73s / 82s）。

### 2.2 `chapter_history`

**现象**

- PR #10 CI 首次 Kernel Check 中 `restore_protects_local_drafts_and_records_provenance`
  返回 `Conflict("本地数据库正在写入，请稍后重试。")`，重跑通过。

**调查**

- 两个用例各自使用独立 tempdir/SQLite，未共享数据库文件。
- 30 次独立执行：**30/30 pass**，每次 0–1s。
- 失败发生在宿主高负载、SQLite busy timeout 5s 到期时；属于环境资源竞争，不是 CAS/事务逻辑错误。
- 未修改产品 busy timeout；避免用延长用户等待时间掩盖环境问题。
