## 4. 观察与判断

1. **不是密钥/网络问题**：密钥可用，模型发现成功；换模型后 Run 进入 running，随后在
   结构化输出校验失败。
2. **不是文学质量问题**：没有正文，无法按 8 维评分；不能给出文学质量结论。
3. **可能是模型不遵守 JSON schema、网关不支持结构化输出参数、或应用 JSON 修复未覆盖**。
   需要读取原始模型响应、检查 planner prompt/schema 与修复路径后再判断。
4. **测试前置条件也可能有影响**：M1 测试书通过 IPC 只填了标题/简介，没有完整的
   bible/story seed。`author-journey` 的本地 Mock 能跑通，但真实模型的结构化输出路径
   仍需用完整项目 setup 或专门的 planner 契约测试复核。
5. **模型选择**：`deepseek-v4.1-flash` 与 `glm-5.3-flash` 均未通过第一个结构化门点；
   在修复或换用可靠的 JSON 模型前，继续跑 M2–M10 没有意义。

## 5. 排查与修复进展

已抓取真实原始响应（不含密钥）并定位到两个问题：

1. **输出截断**：`tokenBudget=4096` 时，deepseek 的 planner JSON 在 1483 字符处截断
   （`setpiece_seeds` 字符串中间），因此解析失败。评测预算已提高到 8192。
2. **字段类型不匹配**：8192 的一次完整响应是合法 JSON，但 `expansion.mystery_box`
   是 5 条字符串的数组，校验要求非空字符串。
3. **模型/网关仍不稳定**：同一 8192 配置的下一次调用又返回了 822 字符的半截 JSON；
   GLM 也出现过截断。应用目前没有对截断 JSON 的“续写/修复”重试，所以 Run 仍会硬暂停。

已提交的修复（Draft PR #20）：

- `story_macro.mystery_box` 为数组时，在校验前按“；”连接为字符串；
- 新增 `story_macro_normalizes_mystery_box_array_to_string` 单元测试。

该修复解决了字段类型问题，但不能单独解决模型/网关的截断输出。M1 仍未通过，M2–M10
仍未执行。
