## 2. Planner / Writer 契约缺口

P17.4.9 的 M1 记录中，计划写“撞见老铁匠被灭口”，正文写成“到达时人已死”。这不是 Schema
解析失败，而是计划只传递短摘要，Writer 没有收到结构化的事件参与者、因果与顺序约束。

修复前的调用链：

```text
用户目标
  -> story_macro（宏观）
  -> character_cast
  -> volume_strategy
  -> chapter_list（只有 title/volumeTitle/summary/characterNames）
  -> context（目标章节计划 JSON）
  -> chapter-draft-v2（只说“不要与上下文冲突”）
  -> consistency-review-v1（issues 只有 type/severity/evidence/suggestion）
  -> chapter-repair-v1（没有义务槽）
  -> 章节候选
```

本轮的契约链：

```text
用户目标
  -> story_macro
  -> character_cast
  -> volume_strategy
  -> chapter_list v2（每章 obligations）
  -> context v2（目标章节计划 + chapter_obligations 来源 + obligationIds）
  -> chapter-draft-v2 + 硬约束块
  -> consistency-review-v2（obligationId + 目标章节计划）
  -> chapter-repair-v2（义务文本 + 冲突 + 候选正文）
  -> 章节候选
```

## 3. 章节义务数据模型

`chapter_list` 的每个章节对象新增 `obligations` 数组：

```json
{
  "id": "ch1-req-1",
  "chapterOrder": 1,
  "type": "required_event",
  "description": "林动亲眼撞见老铁匠被杀",
  "enforcement": "hard",
  "participants": ["林动", "老铁匠"],
  "source": "chapter_plan",
  "evidence": "第1章计划"
}
```

- `type`：`required_event`、`forbidden_event`、`participant`、`causal_constraint`、
  `ordering_constraint`、`continuity_constraint`。
- `enforcement`：`hard` / `advisory`，缺省 hard。
- `id` 全书唯一；缺失时按 `ch{chapterOrder}-{类型缩写}-{序号}` 生成；显式重复 ID 拒绝。
- `participants` 允许字符串或字符串数组；字符串按单参与者处理。
- `source` 缺省 `chapter_plan`；`evidence` 可选，保留规划依据。
- 普通文学描写不升级为 hard；`advisory` 只作为建议。
- 验证结果不写进计划；Reviewer 的 issue 通过 `obligationId`、`evidence`、`severity`
  形成可审计的验证记录。

实现位置：`crates/novel-application/src/obligations.rs`。

## 4. Planner 收口

- `chapter_list` 使用 `chapter-list-v2`，要求每章输出 `obligations`，并明确禁止引用未来章节
  才揭示的事实。
- Planner 上下文从原来的 `volume_strategy + character_cast` 扩展为
  `story_macro + volume_strategy + character_cast`，预算 24k；缺少必要来源仍 fail-closed。
- `validate_structured_output` 对 `obligations` 做确定性归一化与校验；旧计划缺少该字段时
  仍可读取。
- `chapter_plan_for_target` 不再静默返回空计划：在严格上下文组装中返回 integrity 错误，
  预览入口记录 `target_chapter_missing` blocked reason；`execute_context` 将错误转为
  DataIntegrity 暂停，而不是让 Worker 抛裸错误。
- 自由创作 `chapter-draft-v1` 不读取章节上下文，保持原有单 Prompt 行为；新增单元测试锁定。

## 5. Writer 约束注入

- `context` 组装新增必选 `chapter_obligations` 来源；它与 `chapter_list` 一样计入 mandatory
  token 预算，超预算直接报错，不静默裁剪。
- `context` 产物新增：
  - `chapterPlanVersion`
  - `obligationIds`
  - `obligationsText`
  - `trace.sources` 中的 `chapter_obligations` 来源与 content hash
- `chapter-draft-v2` 保持版本不变，但 `draft_prompt` 在渲染后追加“本章硬约束义务”块；
  该块来自冻结的 context 产物，不重新解析计划。
- 义务文本包含 ID、hard/advisory 标签、类型、描述、参与者、来源与依据。
- 未来章节的义务不会进入上下文；Reviewer 也只收到目标章节计划。

## 6. Reviewer 与 Repair

### Reviewer

- 使用 `consistency-review-v2`；上下文只包含 `story_macro + character_cast + 目标章节计划`，
  不再注入整本书的 chapter_list。
- 违反 hard 义务的 issue 必须填写 `obligationId`，且 ID 必须存在于目标计划。
- `validate_structured_output` 保留 `obligationId`、`violationType`、`needsAuthorConfirmation`
  与 evidence；重复 issue 的 identity 也包含 obligationId。
- 未知 obligationId → DataIntegrity 暂停；不进入修复。
- 审校 JSON 无效 → 直接在首次调用后 fail-closed；不再走结构化修复，避免变成空 issues。
- 审校是质量门禁：无效审校不会伪装成零问题通过。

### Repair

- 默认使用 `chapter-repair-v2`（合同显式指定 v1 时仍兼容）。
- Prompt 收到：本章硬约束义务、已确认上下文、审校问题、当前候选正文。
- 明确禁止通过修改计划来迁就正文；只允许正文层面修复。
- 保留一次有界修复、usage 累计、取消令牌传播与失败分类（P17.4.9 已修复）。

## 7. 实际修复的问题

| 问题 | 处理 |
| --- | --- |
| Planner 规划上下文缺 `story_macro` | `chapter_list` 上下文加入 macro，测试断言 |
| 目标章节计划静默缺失 | 严格上下文 fail-closed，预览记录 blocked reason，Worker 暂停 |
| Writer 只收到摘要 | 新增 obligations 来源与硬约束块 |
| Reviewer 无法引用义务 | v2 schema + obligationId 校验 |
| 未知 obligationId | DataIntegrity 暂停，不进入修复 |
| 无效审校 JSON 被修复成空 issues | 审校 JSON 失败直接 fail-closed |
| 章节计划引用未知人物/卷 | 从 Worker 裸错误改为 DataIntegrity 暂停 |
| 未来章节义务泄漏 | context / review 只取目标章节计划 |
| 义务被 token 裁剪 | obligations 必选来源参与预算，超预算报错 |
| 旧计划不兼容 | obligations 可选，旧计划按空义务读取 |
| 修复可改写关键事件 | v2 Repair Prompt 明确不可改写义务 |

7. `worker.rs` 已超过项目 1,300 行硬阈值；本轮把义务逻辑拆到 `obligations.rs`，但 Worker

## 直接回答

**Writer 是否已经可以可靠接收到、追踪并校验章节义务？**

- 可以可靠接收：目标章节的 obligations 是上下文必选来源，超预算会失败，不会被静默裁剪。
- 可以追踪：context 产物记录 `chapterPlanVersion`、`obligationIds`、`obligationsText`，
  Trace 中有 `chapter_obligations` 来源与 hash。
- 可以校验引用：Reviewer 的 `obligationId` 必须存在于目标计划，未知 ID 会暂停。
- 不能保证语义正确：Writer 是否遵守、Reviewer 是否准确判断仍是模型质量；确定性代码只保证
  契约传递、引用完整与 fail-closed。M1 仍需真实模型证据。

**M1 还需要什么实际证据才能判定通过？**

1. 新 Key 与明确授权下的完整 M1 Run。
2. Planner 实际输出目标章节 obligations，且义务覆盖计划中的关键事件、参与者、因果与顺序。
3. Writer 正文不改变 hard 义务；Reviewer 对违反项返回正确 obligationId 与正文证据。
4. 无 high 级时间线/因果矛盾；修复后复验收敛或按设计停在上限。
5. 人工/授权评审记录文学质量与修改成本；Mock 测试不能替代这些证据。
