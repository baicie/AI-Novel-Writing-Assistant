## 架构决策记录 (ADR)

### ADR-001: Trait-Based 处理器设计

**背景**: 需要为多个 HTTP 端点设计统一的处理器框架

**决策**: 使用 Rust trait 而不是宏生成处理器

**理由**:
- 完全的类型安全 (编译时检查)
- 易于扩展新处理器
- 支持依赖注入
- 易于单元测试

**后果**:
- (+) 代码更清晰
- (+) IDE 支持更好
- (-) 需要手动实现每个处理器
- 可接受的折衷

---

### ADR-002: 多层架构 (DTO → UseCase → HTTP → 处理器)

**背景**: 需要清晰的职责分离

**决策**: 采用 5 层架构

**理由**:
- DTO 层独立于业务逻辑
- UseCase 独立于 HTTP 框架
- 易于测试和维护
- 易于替换实现

**后果**:
- (+) 高度可测试
- (+) 独立开发各层
- (-) 增加了复杂度
- 长期收益超过成本

---

### ADR-003: 配置管理 (预定义 + 验证)

**背景**: 需要支持多个环境 (开发、测试、生产)

**决策**: 使用预定义的配置对象 + 显式验证

**理由**:
- 开发和测试环境需要不同配置
- 配置在初始化时验证
- 环境变量可以覆盖

**后果**:
- (+) 配置错误早期发现
- (+) 环境隔离
- (-) 需要显式配置创建
