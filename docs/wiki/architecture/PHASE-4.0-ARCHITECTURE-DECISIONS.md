## 一、Phase 4.0 的核心设计原则

### 1.1 从单体到模块化

**决策**: Phase 4.0 采用分层模块化架构

**原因**:
- Phase 3.0 已验证完整的架构设计
- Phase 4.0 需要构建企业级系统
- 分层模块化便于测试和维护

**架构层次**:

```
┌─────────────────────────────────────┐
│      HTTP / 客户端接口层             │  (Task 4.5)
├─────────────────────────────────────┤
│      应用业务逻辑层                   │  
├─────────────────────────────────────┤
│      数据访问层 (Repository)         │  (Task 4.2)
├─────────────────────────────────────┤
│      认证授权层                      │  (Task 4.3)
├─────────────────────────────────────┤
│      性能监控层 (Prometheus)        │  (Task 4.4)
├─────────────────────────────────────┤
│      数据库存储层 (SQLite)          │  (Task 4.2)
└─────────────────────────────────────┘
```

**实现方式**:
1. Task 4.1 - HTTP 路由和处理器
2. Task 4.2 - Repository 层和数据库
3. Task 4.3 - 认证和授权中间件
4. Task 4.4 - 性能监控和缓存
5. Task 4.5 - 部署和运维

**关键规则**:
- ✅ 层与层之间通过明确的接口通信
- ✅ 不允许跨层直接调用 (绕过中间层)
- ✅ 每层有明确的职责和边界
- ✅ 数据通过 DTO 在层之间传递

---

### 1.2 测试驱动的质量保证

**决策**: 所有功能实现必须跟随测试规划

**测试金字塔**:
```
         △
        /|\
       / | \
      /  |  \  10% - E2E 测试 (集成)
     /   |   \
    /    |    \ 30% - 集成测试
   /     |     \
  /      |      \ 60% - 单元测试
 ────────────────────
```

**单元测试规范**:
- 每个函数至少 1-2 个测试
- 边界值和异常情况必须覆盖
- 测试覆盖率 > 85% (强制要求)
- 100% 测试通过率 (零容错)

**验收标准**:
```
□ 单元测试通过率   100%
□ 代码覆盖率      > 85%
□ 编译警告        = 0
□ 集成测试通过     100%
□ 性能基准达标    100%
```

---

### 1.3 工具自动化优先

**决策**: 所有检查都通过自动化工具执行

**核心工具链**:
```
cargo fmt          → 代码格式化 (必须通过)
cargo clippy       → 代码分析 (0 警告)
cargo test         → 单元测试 (100% 通过)
cargo tarpaulin    → 覆盖率检查 (> 85%)
cargo doc          → 文档生成 (100% 完整)
```

**工作流程**:
```
编码 → 本地验证 → 提交 → CI 验证 → 代码审查 → 合并
      ↑                                    ↓
      └────────────────────────────────────┘
      (所有检查必须通过)
```

**关键原则**:
- ✅ 手动检查只用于最后的审查
- ✅ 所有重复性检查都自动化
- ✅ CI/CD 流程明确和可靠

## 二、Task 4.1-4.5 的设计决策

### 2.1 Task 4.1 - Web 框架 (HTTP 端点层)

**设计决策**:

| 决策项 | 选择 | 理由 |
|--------|------|------|
| **Web 框架** | Axum | 高性能、轻量、Tokio 原生 |
| **异步运行时** | Tokio | Rust 事实标准 |
| **路由分层** | 按功能分组 | 易于维护和扩展 |
| **响应格式** | JSON | RESTful 标准 |
| **错误处理** | 统一 HTTP 错误码 | 一致的客户端体验 |
| **流式响应** | Server-Sent Events | 支持长连接和推送 |

**关键规则**:
- ✅ 每个路由必须返回标准的 ApiResponse<T>
- ✅ 所有错误都映射到标准的 HTTP 状态码
- ✅ SSE 流必须支持中断和恢复

---

### 2.2 Task 4.2 - 数据库集成 (持久层)

**设计决策**:

| 决策项 | 选择 | 理由 |
|--------|------|------|
| **ORM/查询** | SQLx (手工SQL) | 编译时检查，零运行时开销 |
| **数据库** | SQLite (本地) / PostgreSQL (生产) | 开发快，生产稳定 |
| **迁移工具** | sqlx migrate | 版本控制友好 |
| **连接池** | sqlx::Pool | 性能和资源管理 |
| **事务管理** | 显式事务 | 数据一致性保证 |

**关键规则**:
- ✅ 所有数据变更必须使用事务
- ✅ 查询必须使用参数化防止 SQL 注入
- ✅ 迁移脚本必须是幂等的 (可重复执行)
- ✅ Repository 层隐藏数据库实现细节

---

### 2.3 Task 4.3 - 认证授权 (安全层)

**设计决策**:

| 决策项 | 选择 | 理由 |
|--------|------|------|
| **认证方式** | JWT | 无状态、可扩展 |
| **密码加密** | Bcrypt | 标准、安全 |
| **令牌有效期** | 24 小时 | 安全和用户体验平衡 |
| **刷新令牌** | 支持 | 提高用户体验 |
| **授权模型** | 基于角色 (RBAC) | 灵活，易于扩展 |

**关键规则**:
- ✅ 所有密码必须使用 Bcrypt 加密
- ✅ 所有API端点必须进行令牌验证
- ✅ 敏感操作必须记录审计日志

---

### 2.4 Task 4.4 - 性能监控 (观测层)

**设计决策**:

| 决策项 | 选择 | 理由 |
|--------|------|------|
| **监控系统** | Prometheus | 事实标准、开源 |
| **缓存方案** | 内存缓存 (可扩展为 Redis) | 快速，适合开发 |
| **追踪系统** | OpenTelemetry 格式 | 标准化、云友好 |
| **指标暴露** | /metrics 端点 | Prometheus 标准 |
| **缓存策略** | TTL 过期 | 简单、可预测 |

**关键规则**:
- ✅ 所有 HTTP 端点都应有时延指标
- ✅ 所有数据库查询都应有性能指标
- ✅ 缓存命中率 > 80% (目标)
- ✅ p95 响应时间 < 100ms (目标)

---

### 2.5 Task 4.5 - 部署运维 (交付层)

**设计决策**:

| 决策项 | 选择 | 理由 |
|--------|------|------|
| **容器化** | Docker | 标准化、可重复 |
| **编排** | docker-compose | 开发简单、生产可升级 |
| **CI/CD** | GitHub Actions | 原生集成、免维护 |
| **文档** | OpenAPI/Swagger | 标准、自动生成 |
| **发布策略** | 语义版本 + Git Tag | 清晰、可追溯 |

**关键规则**:
- ✅ Dockerfile 使用多阶段构建
- ✅ 所有依赖都固定版本
- ✅ CI/CD 必须包括构建、测试、覆盖率检查
- ✅ 每个发布都必须有 Release Notes

## 三、跨 Task 的设计约束

### 3.1 接口契约

**HTTP API 契约**:

所有响应必须遵循以下格式：

```rust
pub struct ApiResponse<T> {
    pub status: u16,           // HTTP 状态码
    pub message: String,       // 人类可读的消息
    pub data: Option<T>,       // 业务数据
    pub error: Option<String>, // 错误详情
    pub timestamp: DateTime<Utc>, // 时间戳
}
```

**数据库契约**:

所有表必须包含以下字段：
```sql
id TEXT PRIMARY KEY,           -- UUID
created_at TIMESTAMP,          -- 创建时间
updated_at TIMESTAMP,          -- 更新时间
deleted_at TIMESTAMP NULLABLE, -- 软删除
```

---

### 3.2 错误处理

**三层错误处理**:

```
应用层错误 → HTTP 错误码 → 客户端
   ↓            ↓           ↓
Domain Error  500        Internal Server Error
Logic Error   400        Bad Request  
Auth Error    401        Unauthorized
```

**关键原则**:
- ✅ 所有错误都必须有明确的类型
- ✅ 错误必须映射到合适的 HTTP 状态码
- ✅ 敏感信息不能泄露给客户端

---

### 3.3 日志和追踪

**日志级别**:
```
ERROR   → 系统错误、数据错误
WARN    → 潜在问题、性能警告
INFO    → 主要业务事件
DEBUG   → 详细执行流程
TRACE   → 非常详细的诊断信息
```

**追踪原则**:
- ✅ 每个请求有唯一的 request_id
- ✅ 关键业务操作必须记录日志
- ✅ 所有错误都必须记录完整堆栈

## 五、架构衍化路线

### 5.1 Phase 4.0 (当前)

```
单体应用 (Monolith)
  ├─ HTTP 层 (Axum)
  ├─ 业务层 (Service)
  ├─ 数据层 (SQLite)
  └─ 监控层 (Prometheus)
```

### 5.2 Phase 5.0+ (未来)

可能的演化方向：

```
微服务 (Microservices)
  ├─ API Gateway
  ├─ Auth Service
  ├─ Novel Service
  ├─ Chapter Service
  └─ LLM Service

分布式:
  ├─ PostgreSQL (主数据库)
  ├─ Redis (缓存)
  ├─ RabbitMQ (消息队列)
  └─ Kubernetes (编排)
```

**演化原则**:
- ✅ 当前阶段优先考虑**单体 + 模块化**
- ✅ 每个模块都是**独立可测试**的
- ✅ 接口层清晰，便于**后续分解**

## 六、关键决策记录

| 决策 | 选择 | 替代方案 | 权衡 |
|-----|------|--------|------|
| 框架选择 | Axum | Rocket, Actix-web | 性能 vs 开发速度 (选择性能) |
| ORM 选择 | SQLx (手工SQL) | Diesel, Sqlx Macros | 查询优化 vs 类型安全 (并重) |
| 缓存方案 | 内存缓存 | Redis | 部署复杂度 vs 性能 (优先简化) |
| 认证方式 | JWT | Session | 无状态 vs 撤销速度 (选择无状态) |
| 测试覆盖 | > 85% | 50-70% | 质量 vs 开发速度 (优先质量) |
