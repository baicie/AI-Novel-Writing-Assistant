# 正文章节编辑闭环

## Background

章节编辑器同时处理作者手动输入、服务端保存版本和 AI 局部改写候选。三者的时间顺序可能不同：作者继续输入时，章节列表会收到新版本；AI 候选返回时，原文可能已经变化；保存请求发出后，另一个窗口也可能先保存。若编辑器把展示文本、保存文本和 AI 目标片段混成一份状态，就会出现选区错位、旧内容覆盖新内容或保存后重复消耗章节诊断的问题。

## Decision

编辑器以“正文中心、候选先预览、用户确认后写入”为唯一交互闭环。正文坐标使用规范化后的原文 UTF-16 偏移，规范化只处理换行符，不裁剪空格、不删除空段、不把单换行改写成空格。服务端与客户端共用同一套段落和选区替换规则。

光标续写沿用同一条闭环，但目标范围是长度为零的插入点。客户端发送正文快照、UTF-16 光标偏移和前后段落窗口；服务端只返回要插入的新增正文候选，并把候选 diff 锚定到该插入点。接受候选时仍先创建快照、再用当前正文和光标偏移做写回校验，避免把续写插入旧位置。

保存和接受 AI 候选必须携带打开时拿到的 `updatedAt`。服务端在写入前检查版本，发现版本变化就拒绝旧写入；编辑器保留本地草稿，作者可以先加载新的保存版本，再重新选择正文并生成候选。接受候选前先创建正文快照，候选只能替换仍与生成时完全一致的目标片段。

章节工作区诊断属于按需 AI 能力。保存正文或接受候选只刷新章节资料，不自动重新请求章节诊断；作者通过“重新分析本章”主动获取新的诊断，避免普通打字和保存动作重复消耗 Token。页面刷新或服务端推送新版本时，干净编辑器跟随新版本；有未保存输入时保留本地草稿并提示作者选择。

## Current Rule

- `shared/types/chapterEditor/document.ts` 是跨端正文坐标和替换规则的唯一来源。
- `useChapterDraft` 负责编辑中的正文、最近保存正文、保存版本时间和会话草稿恢复，不能由页面组件再维护第二份正文真源。
- AI 预览请求必须保留目标片段的 `from`、`to` 和原文；应用候选前再次校验原文，失败时要求重新选区。
- 光标续写请求必须保留 `contentSnapshot`、`cursorOffset` 和上下文窗口；光标候选只能作为插入操作应用，正文变化或偏移越界时要求重新定位光标。
- 光标工具条提供“继续写下一段、生成过渡段、增加对话、增加环境描写、增加心理描写、推进冲突”和自定义方向；所有方向都先生成 2 到 3 个候选，再由作者接受。
- `updateChapter` 的 `expectedUpdatedAt` 是编辑器保存和候选接受的并发保护字段；其他后台写入不得绕过章节生命周期的版本约束。
- 任务中心只展示运行记录和影响分析。半自动导演的“确认手动修改并继续”应继续放在小说工作区或正文编辑来源页，由作者看到正文上下文后执行。
- 问题关闭必须回到正文来源页：诊断卡只有在 AI 结构化结果引用真实开放问题 ID 时才显示关闭入口，正文存在未保存修改时禁止关闭；关闭后主动重新分析本章，确认新的正文状态。
- 候选改写的差异按连续变更分组，删除与新增相邻时视为一个原子替换；作者可以只勾选需要写回的差异，未勾选部分保留原文，避免“只接受新增”造成重复正文。
- 章节版本入口必须在当前正文编辑页提供上下文预览：服务端只从小说快照中提取当前章节，客户端先将版本载入本地编辑区，用户保存后才写入正文，不能把整本小说恢复动作放进章节编辑器。
- 正文保存入口同时支持按钮和 `Ctrl/Cmd+S`；快捷保存只提交当前草稿，不触发 AI 诊断，保存成功后应刷新本章版本查询，确保刚创建的保护快照马上可见。
- 从历史版本载入正文后，首次保存必须先为当前已保存正文创建手动保护快照，再写入载入内容；普通编辑保存不创建额外快照，避免版本回看操作造成当前正文不可追溯。

### 选区改写的计费状态（P17.2）

选区改写不建 Run、不写候选表、不动正文，因此它不能借用 RunContract 的计费语义。桌面端用 `chapter_selection_rewrite_attempt` 表记录每次请求走到哪一步：

| 状态 | 含义 | 能否免确认重试 |
| --- | --- | --- |
| `not_sent` | 密钥、校验或路由在发送前拒绝 | 可以 |
| `sending` | 已登记、请求进行中；进程崩溃会停在这里 | 不可以 |
| `failed` | 已发出并拿到明确失败，或模型返回了不可用结果 | 不可以，重试会再次计费 |
| `unknown` | 超时、连接中断等无法确认结果的情况 | 不可以 |
| `succeeded` | 已拿到候选 | 不需要 |

规则：

- 同一条 `requestId` 在 `sending` / `unknown` / `succeeded` 状态下再次进入会被拒为 `CONFLICT`，从源头阻止双击或界面重试造成重复计费。
- 内核在错误里同时给出机器可读的 `details.sentState`：`NOT_SENT` / `SENT_BUT_UNUSABLE` / `RESULT_UNKNOWN`。前端优先按它判断「能不能免确认重试」，不能靠中文文案猜测；没有该字段的旧错误结构一律按可能计费处理，只有 `RESULT_UNKNOWN` 还能从错误码识别。
- 错误码与发送状态一一对应：`VALIDATION`（发送前拒绝）、`MODEL_RESULT_UNUSABLE`（已发送且模型返回，但非法 JSON 或空候选）、`MODEL_RESULT_UNKNOWN`（结果无法确认）。模型已经返回的输出问题不能复用 `VALIDATION`，否则界面会把一次已计费的调用当成免费重试。
- 任何无法识别的发送状态都按「可能已计费」处理；`unknown` 仍然禁止自动重发。
- 重新生成前若存在未确认请求或上次结果是 `unknown`，必须先经过作者确认；提示文案要说明「可能已经发送、重新生成会再次调用模型」。
- 未确认请求按 `novel_id + chapter_id` 隔离，不能跨章提示，也不能阻止其它章节继续写作。
- 该表只存状态、时间与简短原因，不存正文、提示词、端点或凭据。

### 编辑位置恢复（P17.2）

重新打开桌面版时，作者应当能接着上次的位置写。位置恢复分三层：

| 层 | 存储 | 说明 |
| --- | --- | --- |
| 最近写作章节 | `localStorage` 的 `ai-novel:edit-position:v1:recent` | 跨书索引，只记 `novelId` / `chapterId` / `updatedAt` |
| 章内位置 | `ai-novel:edit-position:v1:<novelId>` | 光标 UTF-16 偏移、滚动像素、记录时的正式版本与正文长度 |
| 右侧页签 | `chapter-workbench-tab:<novelId>` | 同一本书切章保持，重启后也保持 |

规则：

- **启动不自动跳转**。应用停在首页，由首页「继续上次写作」入口带作者回到该章；自动跳转会打断「先看整体进度」的常见动作，也会让未迁移接口的页面被意外加载。
- 恢复光标必须等编辑器用当前正文重建完成（`editorSeed` 已更新、正文一致）之后再应用；提前设置会按旧坐标落到错误位置。
- 正文长度明显变短（不足原长一半）或光标偏移越界时放弃恢复，绝不把光标夹到末尾。
- 位置按小说隔离，记录只含坐标与标识，不含正文与任何凭据。
- 光标变化与滚动都会调度一次 400ms 的去抖上报；只监听滚动会漏掉「只点了光标没滚动」的情况。

## 章节连续性与上下文来源（P17.3）

章节工作台要在不新建记忆引擎的前提下回答「截至这一章，哪些事实已经确认」。

- **As-Of 规则**：只读取 `effective_chapter_order <= 目标章节顺序` 的事实；
  只把 `confirmed` 且来源章节当前正式版本等于 `source_revision` 的事实放进有效集。
- **来源状态**：来源版本变化 → `stale`；来源章节缺失 → `unavailable`。
  两者都不能继续冒充有效证据；`stale` 提供重新确认入口。
- **候选与冲突**：候选必须由作者确认后才写入正式状态；过期候选禁用确认；
  冲突复用既有 `memory_conflict` 流程，双方来源并列展示，不自动覆盖。
- **上下文预览**：复用 `assemble_director_context` 与 `ContextTrace`，允许必要来源缺失
  但返回 `blockedReasons`；只返回 trace，不返回 Prompt 正文，不调用模型，预算硬上限 64k。
- **历史运行**：context step 的 trace 存在冻结 artifact 里；只读该 Run 自己的记录，
  不用数据库最新状态替换。
- **边界**：章节目录只读 header（不加载正文）；结构化事实 500、候选 200、冲突 100；
  界面关键事实最多展示 80 条并提示剩余数量。

## 伏笔生命周期与剧情因果（P17.4）

- `plot_thread.status` 是伏笔生命周期的唯一权威：open / developing / resolved / deferred /
  abandoned / stale；不再引入第二套伏笔状态字段。
- 每次 setup / develop / payoff / defer / abandon / recover 追加一条 `plot_thread_event`，
  记录章节、来源版本、证据、前后状态与 commandId；历史事件不覆盖。
- 状态转换必须带 `expectedVersion` 与真实章节证据；同一 commandId + 请求哈希幂等返回，
  不同请求冲突。推进/回收章节不能早于埋设章节。
- As-Of：伏笔状态与来源取「目标章节之前最近一条事件」；未来章节的回收不能提前显示。
  最近一条事件来源失效时显示 stale，必须用新证据恢复，不能退回更早状态冒充有效。
- 章节改写时在同一事务内把伏笔置为 stale；结构化事实、角色状态、时间线同步失效。
- 因果边只允许引用同书的事件、伏笔或已确认事实；拒绝自引用与循环；来源失效后边保留但
  `sourceValid=false`。
- 时间线读取有上限（500），不加载全书正文；没有可靠故事内日期时只使用章节顺序。
- 模型建议不能直接改变伏笔状态或创建正式因果边；必须由作者操作。

### 生命周期状态、来源有效性与展示状态（P17.4.1）

- 一次伏笔读取必须区分三个字段：
  - `lifecycleStatus`：截至目标章节由事件折叠出的生命周期状态；
  - `sourceValid` / `evidencePresentInCurrent`：最近一条事件的来源版本与证据是否仍匹配当前正文；
  - `status`：给作者看的综合状态，来源失效且生命周期仍活跃时显示 `stale`。
- `storedStatus` 是数据库原始值，失效流程可能把它改成 `stale`；不要把 `storedStatus` 当作历史语义。
  需要显示“来源失效前是已回收/推进中”时使用 `lifecycleStatus`。
- 旧记忆写入路径可能留下 `disputed`（待确认）与 `superseded`（已被新事实替代）。它们只读展示，
  不参与生命周期动作；`disputed` 的裁决仍走记忆冲突入口。
- 旧 `plot_thread` 行没有事件历史时，`resolved` 只在 `resolved_chapter_order <= As-Of` 时显示；
  不能把当前状态直接回填到更早章节。没有证据的旧行显示 `stale`，作者可用新证据恢复。
- `list_story_facts` 是可信事实读取面：事件来源失效、`stale`/`superseded`/`disputed` 状态、
  以及没有来源证据或来源版本无法核对的旧行都不进入 Director 上下文；数据仍保留在工作台，
  由作者补证据后恢复。不要用删除旧行的方式处理兼容。
- 动作白名单按“展示状态”判断：存储里仍是 `resolved`/`deferred` 但来源失效时，作者仍可用
  `recover`/`payoff`/`abandon` 修复，不能因为存储值而拒绝所有动作。
- 新动作的章节顺序必须不早于已有最新事件；否则新增事件会被更晚事件遮住，造成当前行状态与
  As-Of 折叠不一致。界面在更早章节隐藏动作，并提示到最新动作所在章节继续。
- 事件折叠按“当前章节目录顺序”计算，章节重排后 As-Of 位置随来源章节移动；同一章同一毫秒
  的多次动作按 `rowid`（真实写入顺序）折叠，不能按 commandId 字典序。
- 记忆候选重新确认只能把 `disputed` 提升为 `open`；不得重开 `resolved`/`abandoned`/`stale`，
  也不得覆盖作者最近一次动作的来源章节、版本与证据。
- 时间线合并事件与故事事实时，先按章节顺序、再按事件写入时间排序；超过 500 条保留最近条目，
  丢弃最早条目。伏笔事件来源失效仍保留在时间线，但必须显示“来源失效”。
- 因果边保留历史；端点事件被替代、事实失效或来源章节删除时，`fromValid`/`toValid` 变为 false，
  界面显示“引用对象失效”，不能静默消失或伪装为有效。

## Failure Modes



- 只比较章节 ID：旧窗口会覆盖新正文。应使用 `expectedUpdatedAt` 并在冲突后保留本地草稿。
- 对正文 `trim` 或压缩空白：会改变选区偏移，导致 AI 候选替换错误位置。应保留原文空格、空段和单换行。
- 保存后无条件刷新工作区：会再次调用诊断 AI，把普通保存变成额外用量。应使用显式“重新分析本章”。
- AI 候选返回后直接写入：用户在等待期间的输入会丢失。应先校验目标片段，再创建快照并接受候选。
- 把续写文本当成选区替换：光标前后会出现重复文字或插入位置漂移。应使用长度为零的目标范围和共享的插入函数。
- 让 AI 建议卡直接关闭审校问题：新建议可能没有对应的持久化问题记录。应要求结构化结果带真实问题 ID，并在客户端过滤未知 ID。
- 把每个 diff token 都当成独立接受项：替换通常同时包含删除和新增，拆开接受会重复或残留原文。应先聚合为插入、删除或替换三个原子变更，再执行局部写回。
- 把整本小说版本恢复当成本章撤销：会覆盖其他章节和规划。章节编辑器只允许查看本章版本并载入草稿，真正写入仍走带 `expectedUpdatedAt` 的章节保存链路。
- 载入旧版本后直接覆盖当前正文：如果首次保存没有先保护当前内容，作者无法回到载入前的版本。应记录载入来源，并让首次保存先创建章节范围内的手动快照。
- 把超时或连接中断描述成「失败，请重试」：请求可能已经到达模型服务，直接重试会重复计费。应标记为结果未知，并在重试前要求确认。
- 启动时按「最近章节」自动跳转：会跳过首页概览并触发未迁移接口。应改为首页显式入口。
- 只凭 localStorage 里的旧坐标恢复光标，不校验正文长度：版本变短后光标会停在不相关的文字中间。应比较记录长度并在明显缩短时放弃。
- 用固定的二维 LCS 对比整章改写：长章节会耗尽内存或长时间阻塞编辑器。应先按码点裁掉公共前后缀，再在预算内做精确对比；超出预算时退化为段落级对齐或整段替换，并通过 `degraded` 明确告知作者，不能悄悄给出错位的细粒度对比。

- 用未来章节的事实生成当前章节：会让角色提前知道尚未发生的事。所有连续性查询必须带
  `effective_chapter_order <= 目标顺序`，并检查来源修订仍有效。
- 把记忆候选或 disputed 事实当成 confirmed：会未经作者确认写入正式设定。候选必须走确认命令，
  disputed 只用于冲突展示。
- 用「最新数据库状态」渲染历史 Run 的上下文：会篡改已冻结的运行证据。历史 Run 只能读
  自己的 context artifact。
- 为了做连续性面板而加载全书正文：章节再多也会拖慢工作台。只读章节 header 与按上限过滤的事实。
- 把 `stale` / `unavailable` 静默丢弃：作者会以为事实仍然有效。必须显示来源状态与重新确认入口。
- 用不可审计的 Prompt 字符串代替 Context Trace：作者无法判断上下文为什么缺失或被排除。
  预览与运行都保留结构化 trace。

- 把「计划回收」写成 resolved：会提前剧透并让上下文引用尚未发生的事实。只有作者 payoff
  动作且证据有效时才设置回收章。
- 伏笔状态只看当前行：会把第 10 章的回收泄露到第 5 章。必须按事件 As-Of 推导。
- 来源改写后回退到更早状态：会让作者误以为伏笔仍有效。最近事件来源失效必须显示 stale。
- 用 `storedStatus` 代替 `lifecycleStatus` 展示历史：失效流程把行改成 stale 后，界面会丢掉
  “来源失效前已回收/推进中”的语义。
- 时间线截断保留最旧 500 条：界面提示“最近条目”却展示最早历史。必须丢弃最早条目。
- 在较早章节对更后章节推进过的伏笔执行动作：新事件排不到最新，当前行状态与后续 As-Of 折叠分叉。
- 允许因果边自引用或成环：会破坏因果解释。建立边时做同书实体校验、自引用拒绝与 DFS 环检测。
- 因为时间线需要而扫描全书正文：章节多时会拖慢工作台。只读章节 header、事件与按上限过滤的来源。
